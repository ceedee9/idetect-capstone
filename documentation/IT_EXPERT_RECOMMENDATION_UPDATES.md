# IT Expert Recommendations — Implementation Updates

**Updated:** October 15, 2026

This document brings together the changes made so far in response to the IT experts' recommendations. In simple terms, it explains what changed, how it was approached, what was delivered, and what is still pending.

## Implemented

### Beneficiary app

- **Dispute types:** Added an **Other** option in English and Filipino. The API accepts and stores it as a distinct type, while keeping the existing dispute categories.
- **History:** Combined verification activity with beneficiary-submitted disputes and reports in one chronological, paginated timeline.
- **Language and readability:** Improved English/Filipino labels and date display, and added an **EN / FIL** selector that clearly marks the selected language.
- **App identity and status:** Updated the header to **iDetect / Beneficiary Portal** and redesigned the status card. The beneficiary ID is labeled and masked by default, with a control to show or hide it.
- **Network errors:** Added clear retry options when History, Disputes, or Notifications cannot be loaded, rather than showing an empty list that could be misleading.
- **Test setup:** Fixed the beneficiary widget smoke test's locale and Material widget setup.

### Admin portal and API

- **F-01 — Staff logout auditing (partial):** Added a staff logout API endpoint that records logout events in the audit log. The portal sends the session token explicitly, and idle timeouts are recorded with the reason `idle_timeout`, distinguishable from a manual logout.
- **Authentication availability hardening:** Separated authentication rate limiting from the general API request budget. Normal portal activity can no longer consume the shared limit and prevent a staff member from signing in after a session expires. Sign-in and related authentication endpoints now use their own controlled limit, while ordinary API traffic retains the general limit.
- **F-01 — Establishment authentication auditing:** Establishment successful logins, failed password attempts, lockouts, password changes, and logout events are now recorded. Logout reasons include `manual` and `idle_timeout`. Failed-login events store only a reason and attempt number; passwords, tokens, and other secrets are never stored. The security report includes failed logins.
- **F-01 — Focused authentication auditing:** Staff failed-password attempts now create `login_failed` events. Beneficiary successful logins and normal OTP requests remain intentionally unlogged to avoid high-volume, low-value records. Security-relevant beneficiary events are logged instead: suspended-account authentication attempts and OTP/PIN lockout thresholds, with the authentication method and reason but no OTP, PIN, ID number, or token. Beneficiary logout auditing is deferred to the future roadmap.
- **F-01 — Establishment login guidance:** Login attempts for pending, suspended, and revoked establishments are rejected without issuing a token and return a specific status message. The beneficiary-facing login screen displays that message instead of replacing it with a generic login error.
- **F-01 — Establishment transaction auditing:** Establishment fraud-flag submissions now create a `flag_created` audit event linked to the fraud-flag record, establishment, and verification log. The event records only operational context (beneficiary type, verification outcome, and supplementary status), not the full ID number.
- **F-01 — Agency-scoped audit logs:** Audit-log lists, exports, reports, and case timelines now apply the same agency boundary. OSCA sees senior-citizen records, PDAO sees PWD records, and BPLO sees establishment-side activity; system-generated and establishment-originated events are included only when they match the requesting agency's scope.
- **Staff portal notifications:** A database trigger now creates a deduplicated, privacy-safe alert for the matching office on every dispute insert, independent of which API instance or beneficiary submission path handled it. The trigger migration was applied to the shared database and backfilled the recent test dispute that had no alert. The portal bell polls every 15 seconds, supports read/dismiss actions, and links to the dispute queue. Fixed a route-order bug that made the local alerts endpoint return HTTP 400, scoped alert access to the matching office for both Admin and Super Admin accounts, and made portal load failures visible. A rolled-back insert test verified the trigger creates the OSCA alert; both local and configured deployed APIs returned the alert for the latest test dispute.
- **F-10 — Suspension reason length:** Limited establishment suspension reasons to 2,500 characters. The API rejects longer reasons before changing the record; both BPLO suspension forms use a text area with a live character counter and stop accepting input at the limit.
- **F-09 — Time-bound beneficiary suspensions:** Added required suspension start/end dates and a required reason for new suspensions, with a maximum reason length of 2,500 characters. Both staff-portal suspension entry points now show the reason field, live counter, and date fields, and the API independently validates the complete payload. Suspensions are not automatically cleared: after the end date, the record remains suspended and is marked for staff review. The API creates daily staff reminders starting seven days before the end date and on overdue records. Beneficiary OTP/PIN login responses explain the suspension status, days remaining, end date, and when office review is required. The beneficiary app also shows the same information on the status screen. Staff must manually reinstate, extend, or revoke the record.
- **F-04 — Reference numbers:** Records now get a readable number generated by the database: disputes `DSP-2026-000123` (this also covers business-refusal reports), fraud flags `FLG-…`, establishments `EST-…`, beneficiaries `BEN-…` and verification logs (ID scans) `VER-…`. Existing records were numbered oldest-first. The staff portal shows the number on the Disputes, Fraud Flags, Establishments and Beneficiaries pages and lets staff search by it. A fraud flag also shows the reference of the scan it came from, the scan response and the verification CSV export include it, and the beneficiary app shows it on disputes and on each History transaction. A shared database function makes it a one-line change to number another record type.
  - *Evidence protection:* verification logs cannot be edited, so numbering the old ones temporarily lifts the "no update" rule inside a single all-or-nothing database step and restores it immediately. The test confirmed edits and deletes are still blocked afterwards.
- **F-04 — Filtered audit reports:** The Audit Logs page has a **Reports** button. Admins choose a report type (activity summary, staff activity, security and access, data export log), a period (month, quarter, half year, full year or custom dates), summary or detailed output, grouping (month, action or staff member) and office/role. They can preview before downloading a CSV. Each CSV starts with a cover block (report, period, filters, who generated it, when, record count). Every download is itself written to the audit log, and detailed reports are capped at the newest 50,000 records. Not yet built: PDF output and per-record history reports.
  - *Report quality controls:* Security reports include login, logout, password, and OTP activity. Export reports include normal exports, generated reports, and breach-incident report exports. Invalid roles, unsupported actions, impossible dates, and invalid custom ranges are rejected instead of producing misleading results. Summary totals and export audit counts exclude the display-only `TOTAL` row.
  - *CSV safety:* Both the new report export and the original audit-log export correctly escape commas, quotes, line breaks, and spreadsheet formula prefixes.
  - *UI improvements:* The report modal is centered in the visible viewport, keeps its action buttons close to the form, scrolls long content internally, and clearly highlights the selected report type.
- **F-04 — Court-case file:** The Reports window has a **Case file** tab. Staff type any reference number (DSP-, FLG-, VER-, EST- or BEN-) and get one CSV with the record, the related scan, flags and disputes, and the full audit timeline (oldest first). ID numbers are masked except the last 2 characters, OSCA and PDAO admins can only open records of their own beneficiary type, and each download is written to the audit log.
- **F-01/F-04 — Affected-record display:** The audit log keeps `target_table` and `target_id` for reliable internal linking, while the portal now presents an **Affected record** value using readable references and names such as `Establishment: KFC · EST-2026-000123`. Login, logout, failed-login, lockout, and related authentication events display **Session event** instead of a blank value because they do not affect a database record. Raw technical identifiers remain available in the detail data and machine-readable exports where needed.
- **F-08 — Session timeout policy approved:** The baseline for staff and establishment portals is a **15-minute inactivity timeout**, with a warning during the final **2 minutes** and automatic logout when the 15 minutes expire. This is long enough for staff to review records, consult paper documents, speak with beneficiaries, or complete a legitimate transaction without repeated data loss, while still limiting exposure on an unattended workstation. A two-minute timeout for the entire portal was not selected because it would cause frequent interruptions and could encourage unsafe workarounds such as shared accounts or leaving sessions open. The policy will also add an **8-hour absolute session lifetime**, so activity cannot keep one authentication session valid indefinitely.
  - **Remember me:** Remember me may affect session persistence across browser restarts, but it must never bypass the inactivity timeout, the absolute lifetime, or reauthentication requirements.
  - **Sensitive actions:** Full ID/date-of-birth reveal, sensitive exports and case files, beneficiary suspension or reinstatement, role or permission changes, password resets, and invitation administration should use step-up confirmation or reauthentication rather than a disruptive two-minute global timeout.
  - **Beneficiary app target:** The mobile app should use a shorter protected-screen lock or reauthentication threshold of approximately **5 minutes** when inactive. This protects a lost or shared phone without forcing a complete account sign-out after every brief interruption.
  - **Implementation sequence:** First document and test the current 15-minute staff-portal behavior and its `idle_timeout` audit event. Next add the absolute lifetime and ensure Remember me cannot bypass either limit. Then add step-up protection for sensitive actions. The beneficiary-app lock behavior is a separate phase. No timeout duration is changed by this documentation update alone.
- **Authority model — Phase 1:** Defined agency-scoped BPLO Super Admin, OSCA Super Admin, and PDAO Super Admin roles before implementing F-05/F-06. There is intentionally no overall Super Admin and no cross-agency staff administrator. The model separates each agency's staff governance, establishment Super User management, establishment Regular User operations, and beneficiary self-service. The complete scope and limitations are documented in [AUTHORITY_MODEL_AND_PERMISSION_MATRIX.md](./AUTHORITY_MODEL_AND_PERMISSION_MATRIX.md).
- **Authority model — Phase 2B foundation:** Added the compatibility-backed `establishment_users` table. Existing establishment logins are migrated as establishment Super Users, individual user IDs and roles are included in new establishment tokens, and new verification logs and fraud flags retain the individual establishment user who performed the operation. Legacy establishment credentials remain synchronized during rollout.
- **Fraud-flag cleanup:** Added a permanent-delete action for dismissed fraud flags only. OSCA/PDAO staff receive a clear irreversible-action acknowledgement before deletion, and the deletion is recorded as an immutable `flag_deleted` audit event. Pending and confirmed flags cannot be deleted through this workflow.
- **Authority model — Phase 2C user management API:** Added establishment-scoped endpoints for Super Users to list, create, activate, deactivate, suspend, and reset Regular User accounts. Regular Users are prevented from managing accounts, and all changes are written to the establishment audit trail.
- **Authority model — Phase 2D invitations:** Replaced direct temporary-password creation with a single-use, 24-hour invitation. The invited Regular User sets their own password through the public portal acceptance page before the account becomes active.
- **Authority model — Phase 2E Super User hardening:** Completed the invitation lifecycle. The management screen now shows pending, accepted, expired, and revoked invitation states. Super Users can resend a pending or expired invitation, which replaces the old token with a new 24-hour token, or revoke a pending invitation, which clears the token and permanently invalidates the link. Resend and revoke actions are tenant-scoped, role-protected, and audited. Invitation acceptance is covered by an API regression test that verifies activation, password hashing, token clearing, and the acceptance audit event.

## How the changes were approached

- The beneficiary changes were made across the app and API so the updated dispute type, history, language, and error states work together.
- The suspension limit is enforced in both places: the portal helps staff stay within the limit, and the API independently checks it so the rule cannot be bypassed by sending a direct request.
- Logout auditing records the event and its reason in the existing audit log.
- Audit reports use server-side validation, role/action scoping, bounded result sizes, safe CSV serialization, and an export audit entry rather than relying only on portal controls.
- Establishment invitation lifecycle operations are enforced by the API rather than only by the Flutter controls. Expired invitations are computed as expired when listed, tokens are stored only as SHA-256 hashes, and accepted or revoked links cannot be reused.
- Audit list and report queries resolve affected-record references from the related tables; the technical target fields remain available for investigations.
- Existing behaviors were preserved where possible; recommendations that need a policy decision or more detail were left unchanged.

## Recommendations still pending

- **F-01 remaining:** Establishment token expiry is stateless, so an expired token cannot be actively logged as a separate event without a server-side session store. Beneficiary logout auditing is intentionally deferred; the beneficiary app's local sign-out remains in place. The legacy OSCA, PDAO, and BPLO portals were not changed.
- **Future system roadmap:** Future features and improvements across the beneficiary app, establishment app, staff portals, API, database, security, reporting, privacy, capacity, reliability, and operations are documented in [FUTURE_SYSTEM_ROADMAP.md](./FUTURE_SYSTEM_ROADMAP.md). The roadmap should be updated whenever a useful future enhancement is identified.
- **F-03:** Audit-log retention needs a policy decision.
- **F-04 (remaining):** Audit-log numbering is optional and not done. PDF output and per-record history reports are also not implemented. Report previews are not separately written to the audit log; only CSV downloads are logged. The legacy OSCA/PDAO/BPLO portals do not show the numbers.
- **F-05/F-06:** Implemented default privacy masking for beneficiary API responses,
  fraud/dispute/dashboard views, beneficiary self-service, and CSV exports.
  IDs retain only their final two characters; exact birth dates are omitted and
  excluded from ordinary beneficiary list/detail displays. Verification history/status-sync IDs are also
  masked, and ordinary fraud-flag lists expose only whether restricted OCR data
  exists, not its contents. Raw values remain available only inside
  server-side lookup and write operations. A matching-agency staff member may
  reveal the full ID or exact date of birth from the beneficiary detail page
  when necessary. The detail view requires an acknowledgement warning, uses a
  separate authenticated endpoint, and creates one `sensitive_data_revealed`
  audit event; the ID eye control only changes the display mask within that
  authorized view. The normal detail response remains masked. The audit action
  is registered by migration 040.
  The API also applies this enum addition during startup so a deployed
  database is repaired automatically on the next service restart.
- **Authority model implementation:** Phase 1 is documented and the initial staff API foundation is implemented. The database recognizes agency-scoped Super Admin roles; each can manage only its own office-admin accounts, the final active agency Super Admin cannot be deactivated, and role changes are audited. There is no overall Super Admin. Phase 0 now includes middleware tests for role normalization, regular-admin denial, cross-agency denial, retired-role rejection, and database-backed role refresh. Establishment Super User/Regular User accounts, controlled overrides, and broader route-level authorization tests remain pending.
- **Super User phase remaining operational work:** Apply migrations 042-046 to the deployed database, configure the email provider (`RESEND_API_KEY`, sender, and portal origin), and perform live acceptance tests for delivery, expiry, revoke, resend, tenant isolation, and audit-log visibility. Automatic invitation expiry is intentionally represented as a computed status; no background job is required to mark rows expired.
- Regular BPLO, OSCA, and PDAO Admin accounts now have read-only staff-directory access. Staff creation and account-management mutations are restricted server-side to the matching agency Super Admin.
- **Phase 0 authority verification:** Added automated middleware and staff-route tests for regular-admin denial, matching-agency Super Admin access, cross-agency denial, agency-scoped UUID lookups, database-backed role refresh, deactivated-account rejection, and rejection of the retired global `super_admin` role. The old enum label remains only for PostgreSQL migration compatibility; it is not accepted or provisioned.
- **F-08:** The session timeout policy is now approved and documented above. The staff portal already enforces a 15-minute inactivity timeout with a two-minute warning, and the API now enforces an 8-hour absolute session lifetime by preserving the original login time across silent token refreshes. When that limit is reached, refresh is rejected, stored staff credentials are cleared, and the portal sends the user to sign-in with a specific explanation. The absolute lifetime is intentionally separate from idle timeout: activity can prevent idle logout, but it cannot keep one authentication session valid indefinitely. Step-up protection now covers the exact beneficiary details drawer and sensitive CSV exports/case-file downloads; Remember me safeguards, beneficiary-app protected-screen lock, and live acceptance testing remain pending.
- **F-08 — Step-up protection phase 1:** Opening the exact beneficiary details drawer requires the staff member to re-enter the current password. The API verifies the password against the active staff account and issues a step-up proof valid for five minutes; the sensitive-detail endpoint rejects missing, expired, or mismatched proofs. The proof is short-lived and scoped to the authenticated staff member, so it does not replace the normal session or create a second long-lived login. The full ID unmask button remains available directly from the authorized beneficiary detail page without another password prompt, while the detail drawer remains the deliberate reauthentication boundary. This protects the higher-risk exact birth-date view without creating repeated prompts during ordinary authorized review. Access continues to create the existing `sensitive_data_revealed` audit entry. Sensitive exports and case files remain the next step-up phase.
- **F-08 — Sensitive-detail dismissal rule:** The password acknowledgement cannot be bypassed by closing the modal. Cancel or close returns staff to the beneficiary list instead of leaving the sensitive detail page open. Once the drawer has been opened successfully, the clearly labeled **Reveal ID** button can unmask the ID without asking for the password again; this is intentional because the password was already supplied at the detail-drawer boundary.
- **F-08/F-09 — Status and staff-action acknowledgement:** Beneficiary suspension and reinstatement now require an explicit acknowledgement checkbox before the action can be confirmed. The warning identifies the effect on eligibility and establishment scan results; suspension still requires a reason and start/end dates. Staff account activation, deactivation, and unlocking likewise require a confirmation warning and are recorded in the audit log. These actions intentionally do not require password re-entry because they are already restricted to authorized staff roles. Role/permission changes, if exposed as a future workflow, should require a stronger typed confirmation.
- **F-09:** Implemented with manual review after the end date; automatic reinstatement is intentionally not used. Reinstatement is an explicit, acknowledged staff action.
- **Other deferred items:** Beneficiary photo/visual identification was deferred by request. The matrix does not identify which label should be red, so no label color was changed. Some server-generated notifications may still be in English when the app is set to Filipino.
- **Audit page counts:** Counts currently reflect the rows on the current page, not all matching records.
- **Existing behavior:** Verification notification messages already include the establishment name, so no change was needed for that recommendation.
