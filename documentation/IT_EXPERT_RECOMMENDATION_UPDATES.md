# IT Expert Recommendations — Implementation Updates

**Updated:** October 5, 2026

This document brings together the changes made so far in response to the IT experts' recommendations. In simple terms, it explains what changed, how it was approached, what was delivered, and what is still pending.

## Implemented

### Beneficiary app

- **Dispute types:** Added an **Other** option in English and Filipino. The API accepts and stores it as a distinct type, while keeping the existing dispute categories.
- **History:** Combined verification activity with beneficiary-submitted disputes and reports in one chronological, paginated timeline.
- **Language and readability:** Improved English/Filipino labels and date display, and added an **EN / FIL** selector that clearly marks the selected language.
- **App identity and status:** Updated the header to **iDetect / Beneficiary Portal** and redesigned the status card. The beneficiary ID is labeled and masked by default, with a control to show or hide it.
- **Network errors:** Added clear retry options when History, Disputes, or Notifications cannot be loaded, rather than showing an empty list that could be misleading.
- **Test setup:** Fixed the beneficiary widget smoke test's locale and Material widget setup.

### Admin portal and API

- **F-01 — Staff logout auditing (partial):** Added a staff logout API endpoint that records logout events in the audit log. The portal sends the session token explicitly, and idle timeouts are recorded with the reason `idle_timeout`, distinguishable from a manual logout.
- **F-10 — Suspension reason length:** Limited establishment suspension reasons to 2,500 characters. The API rejects longer reasons before changing the record; both BPLO suspension forms use a text area with a live character counter and stop accepting input at the limit.
- **F-04 — Reference numbers:** Records now get a readable number generated by the database: disputes `DSP-2026-000123` (this also covers business-refusal reports), fraud flags `FLG-…`, establishments `EST-…`, beneficiaries `BEN-…` and verification logs (ID scans) `VER-…`. Existing records were numbered oldest-first. The staff portal shows the number on the Disputes, Fraud Flags, Establishments and Beneficiaries pages and lets staff search by it. A fraud flag also shows the reference of the scan it came from, the scan response and the verification CSV export include it, and the beneficiary app shows it on disputes and on each History transaction. A shared database function makes it a one-line change to number another record type.
  - *Evidence protection:* verification logs cannot be edited, so numbering the old ones temporarily lifts the "no update" rule inside a single all-or-nothing database step and restores it immediately. The test confirmed edits and deletes are still blocked afterwards.
- **F-04 — Filtered audit reports:** The Audit Logs page has a **Reports** button. Admins choose a report type (activity summary, staff activity, security and access, data export log), a period (month, quarter, half year, full year or custom dates), summary or detailed output, grouping (month, action or staff member) and office/role. They can preview before downloading a CSV. Each CSV starts with a cover block (report, period, filters, who generated it, when, record count). Every download is itself written to the audit log, and detailed reports are capped at the newest 50,000 records. Not yet built: court-case file per reference number, PDF output, per-record history reports.

## How the changes were approached

- The beneficiary changes were made across the app and API so the updated dispute type, history, language, and error states work together.
- The suspension limit is enforced in both places: the portal helps staff stay within the limit, and the API independently checks it so the rule cannot be bypassed by sending a direct request.
- Logout auditing records the event and its reason in the existing audit log.
- Existing behaviors were preserved where possible; recommendations that need a policy decision or more detail were left unchanged.

## Deliverables and validation

- Updated beneficiary Flutter app and API behavior. Database migrations `034_add_other_dispute_type.sql`, `035_add_reference_numbers.sql` and `036_add_verification_reference_numbers.sql` are registered; **run the API migrations (`npm run db:migrate`) before using the new dispute type or reference numbers in a deployed environment.** Deploy the migration before the new API/portal: the verification scan and history queries read the new column and will fail until 036 is applied.
- Updated staff portal suspension forms and API validation.
- Staff logout audit endpoint and portal integration.
- Beneficiary widget smoke test passed, and the beneficiary project analyzer reported no errors.
- Suspension API tests passed for both boundary cases: 2,500 characters accepted and 2,501 rejected without a database write.
- Staff portal production build passed.
- Reference-number migrations (035, 036) were verified on a temporary in-memory Postgres: existing rows numbered by date, new rows continue the sequence, re-running is safe, and verification logs still reject edits and deletes afterwards.
- Staff logout auditing was tested and confirmed on the live site.

## Recommendations still pending

- **F-01:** Audit logging for establishment and beneficiary app logouts is not implemented. The legacy OSCA, PDAO, and BPLO portals were not changed.
- **F-03:** Audit-log retention needs a policy decision.
- **F-04 (remaining):** Search and year-end reports grouped by reference number, and the court-case file export. Audit-log numbering is optional and not done. The legacy OSCA/PDAO/BPLO portals do not show the numbers.
- **F-05/F-06:** ID and age masking in API responses remains outstanding pending the audit work.
- **F-08:** Session timeout policy is undecided. The current two-minute recommendation has not been applied.
- **F-09:** Suspension start/end dates and reminders are not implemented; the suspension policy must be decided first.
- **Other deferred items:** Beneficiary photo/visual identification was deferred by request. The matrix does not identify which label should be red, so no label color was changed. Some server-generated notifications may still be in English when the app is set to Filipino.
- **Audit page counts:** Counts currently reflect the rows on the current page, not all matching records.
- **Existing behavior:** Verification notification messages already include the establishment name, so no change was needed for that recommendation.
