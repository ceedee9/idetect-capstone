# IT Expert Testing — Findings Triage & Implementation Plan

**Context:** 3 IT Expert testing rounds surfaced ~50 findings across the OSCA, PDAO, BPLO, Establishment, and Beneficiary sides of iDetect. A local government unit (LGU) is a likely buyer, so this plan weighs every item against **compliance (Data Privacy Act / RA 10173, COA audit rules), security posture, and procurement credibility** — not just dev effort.

Legend:

- **Verdict:** ✅ Adopt · ⚠️ Adopt (modified) · ❌ Reject/defer · 🔁 Already satisfied
- **Effort:** S (hours–1 day) · M (few days) · L (multi-day, schema/architecture change) · XL (new subsystem)
- **Priority:** P0 (compliance/security-critical) · P1 (high value) · P2 (nice-to-have)

---

## 1. Executive Summary

1. **One foundational feature unlocks ~8 other requests:** a global, system-generated **ticket/reference number** on every record (establishment entries, beneficiary entries, disputes, refusal reports, fraud flags). Build this first — it's referenced directly or indirectly by items #10 in the notes, refusal reports, fraud flag reference codes, and the "evidence/timeline/ticketing for court cases" ask. Doing it once, well, is cheaper than patching each module separately later.
2. **Privacy redaction (senior/PWD age, ID number) is a legal exposure, not a preference.** Since OSCA/PDAO handle sensitive personal information of seniors and PWDs, RA 10173 (Data Privacy Act) requires data minimization on anything public-facing. This is P0 regardless of effort.
3. **A handful of asks are trivial UI/copy changes** (red label, "Contact Us" section, "Others" dispute option, all-caps establishment name) — do these in a single cleanup pass, they cost almost nothing and show responsiveness to the testers.
4. **Two items are pushed back on** (2-minute session timeout, email-to-portal auto-routing) — see §4 for reasoning and the recommended compromise.
5. **Procurement angle:** LGU buyers will scrutinize audit trails, retention policy, RBAC granularity, and incident/maintenance procedures more than cosmetic UI. Phases 1–2 below are what a technical evaluation committee will actually check.

## 3. Roadmap (sequenced by dependency, not just priority)

### Phase 1 — Foundation (compliance & architecture-critical, do first)

- Global ticket/reference number system (#10) — unlocks #9, #14, #42
- Audit log login **+ logout** timestamps (#11, #25)
- Retention policy: formalize 1-year minimum + archival job (#3)
- Session timeout tuning: 5-min idle / 2-min warning for portals (#4)
- Senior/PWD data redaction on public/printable views (#13)
- Establishment license number (#22) + suspension timeframe + auto-lift (#20/#41)
- Self-service password reset via email link + masked ID display (#23)

### Phase 2 — Structural (RBAC & accountability)

- Establishment 2-account model: super user + regular user, manager-issued token (#5, #19)
- Super-admin tier that alone can manage staff accounts; staff view-only role (#24, #27)
- Beneficiary edit → notify ID owner with reason (#25)
- Establishment-initiated dispute on behalf of a beneficiary (#37)
- Beneficiary History tab expansion (#39)
- Establishment-scoped audit report (#40)
- OSCA/BPLO bulk audit export by period (#12)
- Bulk upload error/count/success notification detail (#35)
- System-down / maintenance-mode banner (#36, #28)

### Phase 3 — Strategic / large scope

- "Court case" evidence/timeline/ticketing export bundle (#42)
- Beneficiary Website (#43)
- Bilingual (English/Filipino) support (#33)

### Phase 0 — Do anytime, near-zero cost (batch into one cleanup PR)

Flowchart + architecture diagram (#1, #2), suspension reason 2,500-char field (#7), dashboard yearly graph (#6), red label (#16), "Contact Us" section (#31), camera-permission rationale dialog (#32), "Others" dispute option (#34), all-caps "ESTABLISHMENT" + reference code styling (#14), establishment contact/franchise fields (#8), beneficiary photo capture + consent notice (#15/#38).

### Policy-only items (no engineering, write it down)

Database freshness/backup SOP (#18), scheduled maintenance rotation (#28/#29), hotfix process (#30).

## 5. LGU Procurement Considerations

Since a local government purchase is realistic, prioritize what a technical evaluation committee will actually check:

- **Data Privacy Act compliance**: redaction of senior/PWD PII (#13), consent notices for photo capture (#15), retention policy (#3), edit-notifies-data-subject (#25). Consider NPC registration status as a talking point.
- **Auditability**: full login/logout trail (#11), ticket-numbered records (#10), court-case evidence export (#42) — these are the features that make the system defensible in an audit or legal dispute, which matters a lot for government adoption.
- **RBAC granularity**: super/regular establishment accounts (#19), staff view-only + super-admin gating (#24/#27) — government IT departments expect least-privilege access control.
- **Operational maturity**: documented maintenance window, hotfix process, and system-down transparency (#28–#30, #36) signal a production-ready, supportable system rather than a student project.
- **Accessibility**: Beneficiary Website (#43) and bilingual support (#33) support the elderly/PWD user base the LGU is accountable to — good narrative for procurement, but correctly sequenced as Phase 3 since they don't block go-live.

**Suggested next step:** start Phase 1 with the ticket number system and audit log logout tracking — both are referenced by multiple other findings, so building them first avoids rework.
